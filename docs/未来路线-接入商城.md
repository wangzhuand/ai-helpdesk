# 未来路线：接入第三方商城（多租户 SaaS）

> **状态**：未来路线，**现在不实现**。等真有第一个接入方时再按本文档执行。
> **写下来的原因**：避免到时候重新设计；也让现在的代码不要把"访客=匿名"写死，预留扩展点。
> **更新日期**：2026-09-21

## 0. 一句话原则

> **我们不做访客的登录认证，访客的登录态来自接入方（别人商城）。我们只做"签名校验"。**

这是 B2B SaaS 的标准模式（Stripe、Intercom、Crisp 都是）。类比：客服外包团队信任甲方商城的盖章，不去重新查用户身份证。

## 1. 身份认证的责任边界

```
访客 → 在别人商城登录（商城管，我们不管）
       ↓ 商城用约定密钥签一个短时效 token，声明"这是用户 X，X 分钟内有效"
访客 → 带着这个 token 访问我们的客服 widget
       ↓ 我们的网关用同一密钥验签
我们 → 验签通过 → 信任"这是用户 X" → 关联到我们的 visitor 记录
```

我们永远不碰访客的密码、不维护访客的会话过期。

## 2. 三种方案对比

| 方案 | 怎么做 | 评价 |
|---|---|---|
| **A 嵌入式 widget + 签名 token**（推荐） | 客服前端打包成一段 JS，商城页面加载；商城后端用密钥签 token；我们验签 | 业界主流，Intercom/Crisp 都这样 |
| B OAuth 第三方登录 | 客服是 OAuth client，跳商城登录拿 code | 重，适合独立部署的客服控制台，不适合嵌入式聊天 |
| C 商城后端代理 | 所有客服请求经商城后端转发，密钥不暴露给前端 | 最安全但集成最重，一般不必要 |

选 A。

## 3. 真接入时的 5 步

1. **客服前端打包成 widget**：现在 Vue 项目 `vite build` 后改成 widget 模式（`@originjs/vite-plugin-federation` 或自包一层 web component）。一段 `<script>` + 挂载点，类似嵌入百度统计。
2. **接入方配置**：商城在我们的"商户后台"注册，拿到 `app_id` + `app_secret`（每家商城一对密钥）。
3. **签名 token**：商城后端在用户登录后，用 `app_secret` 签一个短时效 token，内容 `{merchant_id, user_id, exp}`，HMAC-SHA256；放在 widget 初始化参数或 `Authorization` 头里。
4. **我们的网关**：写个拦截器（类似现在的 `LoginInterceptor`，但验的是"商城签名"而不是我们发的 JWT）。验签通过后把 `merchant_id + external_user_id` 放进 `UserContext`，关联到 `visitor` 记录。
5. **数据隔离（多租户）**：每张业务表加 `merchant_id`；`visitor` 加 `external_user_id + merchant_id`；知识库按 `merchant_id` 隔离。

## 4. 数据库要做的改动（V2 迁移，现在不做）

```sql
-- visitor 表加两列
ALTER TABLE visitor ADD COLUMN merchant_id BIGINT COMMENT '所属商城';
ALTER TABLE visitor ADD COLUMN external_user_id VARCHAR(64) COMMENT '商城侧的用户id';

-- 其他业务表（conversation / ticket / kb_document / ...）统一加 merchant_id
```

知识库的 `kb_document` 也按 `merchant_id` 隔离——每家商城有自己的 FAQ。
