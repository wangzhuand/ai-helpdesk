# AI 智能客服工单平台（ai-helpdesk）· 项目规划书

> 目标：3-4 个月（按 16 周、每周 25-35 小时估算）完成一个可部署、可演示、可深入面试的项目。
> 投递方向：Java 后端 / AI 应用 / 全栈。

---

## 1. 项目定位

**一句话**：一个以 AI agent 为一线客服的系统——agent 基于知识库回答常见问题、能查单、能建工单，置信度低时自动转人工，后台供人工坐席监控、接管和沉淀知识库。

- **目标用户**：需要客服但养不起客服团队的小团队——独立开发者的产品、网上小店、开源项目维护者。
- **核心价值**：把"常见问题 AI 解决、复杂问题快速转人工"做成一条顺滑的流水线，并用数据（解决率、命中率）证明 AI 干得怎么样。
- **差异化**：市面上学生项目里的"客服系统"大多是工单 CRUD + 挂个聊天插件。本项目的差异化在于 **agent 是主干而非外挂**：整个系统围绕"提高 AI 解决率"设计，带评测集、回归打分、成本统计——这些是 AI 工程岗位最想听的内容。

## 2. 角色与核心流程

**三个角色**

| 角色 | 入口 | 干什么 |
|---|---|---|
| 访客（客户） | 聊天页 /chat | 提问、查订单、申请售后 |
| 坐席（人工客服） | 控制台 /console | 监控 AI 会话、接管回复、处理工单、维护知识库 |
| 管理员 | 控制台 | 坐席管理、评测、统计 |

**一条完整用户旅程（也是 MVP 验收标准）**

1. 访客打开聊天页提问："怎么申请退款？"
2. AI 基于知识库检索，流式输出回答，并附引用来源
3. 访客说"我订单是 A123，退款一直没到账" → AI 调用 `query_order` 工具查单（mock），确认超时，自动创建工单
4. 访客表达不满 / 连续两次检索无结果 / 访客点击"转人工" → 会话转给坐席
5. 坐席在控制台接管会话、回复，处理工单：受理 → 解决 → 关闭
6. 会话结束时访客点"已解决/未解决"，进入解决率统计

## 4. 系统架构

**阶段一（第 1-9 周）：模块清晰的单体**

```
浏览器（访客聊天页 / 坐席控制台）
        │ HTTP / SSE
        ▼
┌──────────────────────────────┐
│  SpringBoot 单体              │
│  会话│消息│工单│知识库│Agent    │
└──────────────────────────────┘
   │          │          │
   ▼          ▼          ▼
 MySQL      Redis       ES 8        GLM API
（核心数据）（缓存/锁/限流）（知识检索） （LLM）
```

**阶段二（第 10 周起）：带理由地拆分**

```
前端 ──► Gateway ──► helpdesk-core ──► MySQL
                        │  │
        OpenFeign+Sentinel │ RocketMQ 事件
             │             ▼
             ▼      notification-service ──► 邮件 / 企微webhook
        ai-service ──► ES + GLM
（Nacos：注册与配置；core 调 ai 熔断降级：AI 挂了自动降级为"直接排队转人工"）
```

拆分理由（面试原话素材）：LLM 延迟高且不稳定，必须与核心会话/工单流程隔离部署；AI 服务故障时核心业务降级可用，而不是整体瘫痪。SSE 连接终止在 core，core 用 WebClient 流式转发 ai-service 响应（进阶可选：改为 MQ + Redis pub/sub 解耦）。

## 5. 功能清单（按模块，标注所属阶段）

**会话与消息（P1）**
- 访客匿名创建会话、发送消息、查看历史（游标分页）
- SSE 流式接收 AI 回复；坐席接管后消息实时下发
- 会话状态：`AI → AGENT → CLOSED`；转人工触发条件：用户点击按钮 / 检索得分低于阈值 / 连续 2 次无结果 / 用户负面情绪
- 会话结束时"已解决/未解决"评价按钮（解决率数据来源）

**知识库（P1）**
- 文档上传（txt/md，PDF 可选）/ 在线文本粘贴
- 分块（起点：按标题分段，500 字/块、重叠 50 字，后续用评测调优）→ embedding → 写入 ES
- 文档状态机：`PENDING → PROCESSING → READY / FAILED`
- 控制台"检索测试"页：输入 query 看召回结果与得分（调试 RAG 神器）

**Agent（P1 基础版，P3 多步版）**
- 基础链路：ES 混合检索 top10 → rerank 取 top3 → 组装 prompt（system：只依据资料回答，无依据则说明并建议转人工 + 资料 + 最近 10 条历史）→ LLM
- 工具（function calling）：`create_ticket`、`query_order`（mock 数据）、`escalate_to_human`
- P3 升级：意图识别 → 检索 → 回答 → 满意度确认 → 建单/转人工的多步链路
- rerank 二选一：让 LLM 从 top10 挑最相关 3 条（省事）或接 bge-reranker 类 API（更专业）

**工单（P1）**
- 工单 CRUD、状态机 `OPEN → PROCESSING → RESOLVED → CLOSED`（+ REOPENED）
- 乐观锁（version 字段）防坐席并发抢单/重复流转；每次流转写 ticket_log
- 列表按状态/优先级/处理人筛选

**坐席与权限（P1）**
- 登录（手写 JWT 拦截器，不引安全框架——面试可讲原理）
- 角色区分：坐席看分配给自己的 + 待接管池；管理员全量 + 管理功能
- 基础防水平越权：只能操作权限内资源

**消息队列场景（P2，RocketMQ）**
1. 知识库文档异步处理：上传落库 → 发 MQ → consumer 分块/向量化（用户不等大文档）
2. 工单/会话事件驱动通知：状态变更 → MQ → notification-service 发邮件/企微 webhook
3. SLA 超时提醒（延迟消息）：工单/待接管会话 15 分钟无人处理 → 自动提醒并升级优先级
4. 失败重试 + 死信队列：通知发送失败重试 3 次进死信，后台可查可补偿

**Redis 深度场景（P2）**
1. 知识库/配置缓存（cache-aside，讲穿透/击穿/雪崩对策）
2. 分布式锁：坐席抢单（Redisson 或 setnx+过期，讲两者差异）
3. 限流：访客调 LLM 的接口按 visitor_id 令牌桶限流
4. 幂等前置：建单请求 setnx 去重 + 数据库唯一索引兜底

**评测（P2，差异化核心）**
- 评测集 50-100 条 QA（自造一个虚构产品"示例商城"的 FAQ 当演示数据，避免版权问题且演示自然）
- 指标：检索命中率 recall@3（rerank 后 top3 是否含标准出处）、回答质量（LLM-as-judge 1-5 分）、会话解决率
- 每次改 prompt/分块参数前跑回归，eval_run 记录版本与分数，形成优化曲线

**统计（P3，可选）**
- 会话量、解决率、工单处理时长、LLM token 成本（llm_call_log 聚合）

## 6. 数据库设计（核心表）

```sql
-- 坐席/管理员
CREATE TABLE sys_user (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  username VARCHAR(32) NOT NULL UNIQUE,
  password_hash VARCHAR(64) NOT NULL,
  nickname VARCHAR(32),
  role VARCHAR(10) NOT NULL DEFAULT 'AGENT' COMMENT 'ADMIN/AGENT',
  status TINYINT DEFAULT 1,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 访客（匿名）
CREATE TABLE visitor (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  nickname VARCHAR(32),
  last_ip VARCHAR(45),
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 会话
CREATE TABLE conversation (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  visitor_id BIGINT NOT NULL,
  agent_id BIGINT DEFAULT NULL COMMENT '接管坐席, NULL=AI处理中',
  status VARCHAR(20) NOT NULL DEFAULT 'AI' COMMENT 'AI/AGENT/CLOSED',
  resolved TINYINT COMMENT '1已解决 0未解决 NULL未评价',
  last_message_at DATETIME,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  KEY idx_visitor (visitor_id),
  KEY idx_status_last (status, last_message_at)   -- 坐席端待接管列表页
);

-- 聊天消息（大表：核心深度点）
CREATE TABLE message (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  conversation_id BIGINT NOT NULL,
  sender_type VARCHAR(10) NOT NULL COMMENT 'VISITOR/AI/AGENT/SYSTEM',
  content TEXT NOT NULL,
  created_at DATETIME(3) DEFAULT CURRENT_TIMESTAMP(3),
  KEY idx_conv (conversation_id, id)   -- 游标分页：WHERE id < #{lastId} ORDER BY id DESC LIMIT 20
);

-- 工单
CREATE TABLE ticket (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  ticket_no VARCHAR(32) NOT NULL UNIQUE COMMENT '对外单号',
  conversation_id BIGINT COMMENT '来源会话',
  title VARCHAR(128) NOT NULL,
  description TEXT,
  category VARCHAR(32) COMMENT '退款/物流/账号/其他',
  priority TINYINT DEFAULT 1 COMMENT '1低2中3高',
  status VARCHAR(20) NOT NULL DEFAULT 'OPEN' COMMENT 'OPEN/PROCESSING/RESOLVED/CLOSED',
  assignee_id BIGINT COMMENT '处理人',
  sla_deadline DATETIME,
  version INT NOT NULL DEFAULT 0 COMMENT '乐观锁',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  KEY idx_status_pri (status, priority),
  KEY idx_assignee (assignee_id, status)
);

-- 工单流转日志
CREATE TABLE ticket_log (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  ticket_id BIGINT NOT NULL,
  operator_id BIGINT,
  action VARCHAR(32) COMMENT 'CREATE/ASSIGN/TRANSFER/RESOLVE/CLOSE',
  from_status VARCHAR(20), to_status VARCHAR(20),
  remark VARCHAR(255),
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_ticket (ticket_id)
);

-- 知识库文档
CREATE TABLE kb_document (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  title VARCHAR(128) NOT NULL,
  source_type VARCHAR(10) COMMENT 'FILE/TEXT',
  status VARCHAR(20) DEFAULT 'PENDING' COMMENT 'PENDING/PROCESSING/READY/FAILED',
  chunk_num INT DEFAULT 0,
  created_by BIGINT,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 知识库分块（内容同步到 ES）
CREATE TABLE kb_chunk (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  document_id BIGINT NOT NULL,
  chunk_index INT NOT NULL,
  content TEXT NOT NULL,
  es_id VARCHAR(64),
  KEY idx_doc (document_id)
);

-- LLM 调用日志（成本/延迟统计）
CREATE TABLE llm_call_log (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  scene VARCHAR(20) COMMENT 'CHAT/RAG/EVAL/JUDGE',
  model VARCHAR(32),
  prompt_tokens INT, completion_tokens INT,
  latency_ms INT,
  success TINYINT,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_scene_time (scene, created_at)
);

-- 评测
CREATE TABLE eval_item (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  question VARCHAR(255) NOT NULL,
  expected_answer TEXT,
  tags VARCHAR(64),
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE TABLE eval_run (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  item_count INT,
  retrieval_hit INT COMMENT '命中条数',
  avg_score DECIMAL(4,2) COMMENT 'judge 均分',
  model VARCHAR(32),
  prompt_version VARCHAR(32),
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

## 7. 接口设计（核心 API）

**访客端**

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /api/v1/conversations | 创建会话（匿名） |
| POST | /api/v1/conversations/{id}/messages | 发消息；AI 处理中时返回 SSE 流（text/event-stream） |
| GET | /api/v1/conversations/{id}/messages?lastId=&size= | 历史消息（游标分页） |
| POST | /api/v1/conversations/{id}/resolve | 访客评价已解决/未解决 |

**坐席控制台（JWT）**

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /api/v1/console/login | 登录，返回 JWT |
| GET | /api/v1/console/conversations | 会话列表（待接管池/我的会话） |
| POST | /api/v1/console/conversations/{id}/takeover | 接管（乐观锁防并发） |
| POST | /api/v1/console/conversations/{id}/messages | 人工回复（SSE 实时下发访客） |
| GET/POST/PUT | /api/v1/console/tickets… | 工单 CRUD 与流转（version 乐观锁） |
| POST | /api/v1/console/kb/documents | 上传/粘贴知识文档 |
| GET | /api/v1/console/kb/documents | 文档列表与状态 |
| POST | /api/v1/console/kb/retrieve-test | 检索测试：query → 召回块与得分 |
| POST | /api/v1/console/eval/run | 跑一次评测 |
| GET | /api/v1/console/eval/runs | 历次分数 |

**统一规范**：返回 `{code, message, data}`；`@RestControllerAdvice` 全局异常；参数校验用 Validation；接口文档用 Apifox 维护（顺便当联调工具）。

## 10. 简历三套话术（占位符后填真实数据）

**后端版**：设计并实现 AI 客服工单平台（SpringBoot/MySQL/Redis/RocketMQ/ES/微服务）。负责：① 基于 RocketMQ 实现文档异步处理、事件驱动通知、延迟消息 SLA 提醒、失败重试+死信队列四个场景；② Redis 缓存/分布式锁/限流；③ 消息大表游标分页与索引优化，压测后将 XX 接口 P99 从 X ms 降至 X ms；④ 拆分 ai-service 并用 Sentinel 熔断降级，AI 服务故障时核心流程自动降级为人工排队。

**AI 应用版**：实现基于 RAG 的智能客服 agent。负责：① ES 混合检索（BM25+向量）+ rerank，检索命中率 recall@3 从 X% 提升至 X%；② 建立百条评测集与自动回归（LLM-as-judge），评测驱动 prompt 与分块策略迭代；③ function calling 实现查单/建单/转人工，AI 会话解决率达 X%；④ token 成本与延迟监控。

## 11. 从 0 开始的开发方法（第一次做项目必读）

**标准开发循环（每个功能都这么走）**
1. 一句话说清这个功能要干什么（写进 todo）
2. 纸上花 10-20 分钟想清楚：要动哪几张表、加哪几个接口、前端哪个页面
3. 后端：entity → mapper → service → controller，用 Apifox 自测通过
4. 前端联调（AI 生成，自己读得懂的部分才合并）
5. 小步 commit（每个 commit 都应是可运行状态）
6. 更新 todo 和决策日志

**四条铁律**
1. **每周五必须有能跑的版本**——宁可功能少，不可全局崩。走"先跑通再完善"的路线，不要三周都在写"底层框架"。
2. **卡壳超过 2 小时就换方法**：把问题缩小到最小复现 / 打日志二分定位 / 带上具体报错和你猜的方向去问 AI。卡住不是失败，硬耗才是。
3. **AI 辅助的边界**：架构和设计自己定（这是面试的命根子），样板代码可以让 AI 写，但合并前必须读一遍——讲不出"为什么这么写"的代码不合入。
4. **允许丑**：MVP 阶段代码丑没关系，第 9-11 周的重构和优化本身就是最值钱的面试素材（"我什么时候、为什么重构"是好故事）。

**决策日志（decision-log.md，从第 1 天就开始记）**

```markdown
## 2026-09-05  消息历史接口用游标分页而不是 offset
- 背景：消息表是增长最快的大表，offset 深翻页全表扫描
- 决策：WHERE id < lastId ORDER BY id DESC LIMIT 20
- 放弃的方案：offset 分页（实现简单但性能差）；ES 存历史（引入一致性复杂度不值）
- 后续验证：第 11 周压测对比两种分页耗时
```

每次做技术选择都记一条，面试前通读一遍——这就是你的"坑与取舍"题库。

**Git 规范**
- 仓库：GitHub 公开仓库，好 README 从第一周就开始维护
- 分支：单人项目用 `main` + 功能分支即可（养成习惯，面试可讲）
- commit 前缀：`feat:` / `fix:` / `docs:` / `refactor:` / `perf:`，小步提交

**后端包结构参考**

```
com.example.helpdesk
 ├─ controller/     // 分 visitor / console 两组
 ├─ service/        // 接口+impl
 ├─ mapper/
 ├─ entity/  dto/
 ├─ config/         // MyBatis-Plus、Redis、ES、MQ、安全等配置
 ├─ common/         // Result、异常、常量、工具
 └─ aspect/         // 后期：日志、限流注解等
```
