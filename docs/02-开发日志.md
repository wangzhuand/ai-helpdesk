**后端 · 2026-09-16 新发现（第 10 项）**

10. ✅ **SSE 客户端断开后不取消 LLM 调用**【2026-09-18 已完成，直接省 token】：
    - 现状：`ConversationController.sendMessage` 里是 `aiService.chatStream(recent).toIterable().forEach(token -> { ... try { emitter.send(...) } catch (Exception ignore) {} })`。`emitter.send` 失败（客户端已断开）被 `catch (Exception ignore) {}` **静默吞掉**，但 `forEach` 会继续把整个 LLM 流消费完 → **用户关掉页面/刷新后，后端仍在跟 DeepSeek 流式对话，全程照付 token**。
    - 改法：注册 `emitter.onCompletion / onTimeout / onError` 三个回调；把 `Flux` 改成 `subscribe(...)` 并持有 `Disposable`，在回调里 `disposable.dispose()` 取消上游；同时别再用 `catch (Exception ignore) {}` 静默吞异常（至少记一条 debug 日志）。
    - 与第 6 项（线程池）的关系：线程池决定"最多同时跑多少个 SSE"，第 10 项决定"每个 SSE 会不会白跑"。**第 10 项的收益更直接**。
    - **实现结果（2026-09-18）**：`toIterable().forEach` → `Flux.subscribe(规则①每来一个 token / 规则②出错 / 规则③正常结束)`；用 `AtomicReference<Disposable>` 持有订阅（lambda 只能捕获 final 局部变量，且开关要等 subscribe 返回才有值）；`onCompletion / onTimeout / onError` 三处注册 `cancelUpstream`（`getAndSet(null)` 保证幂等，且不能做成类成员变量——Controller 是单例，多人并发会互相覆盖开关）；token 转发失败时也主动取消。
    - **有意为之的取舍**：取消（cancel）不等于出错（error），`dispose()` 后规则②③都不触发，所以**半截回答不入库**，避免用户刷新回来看到一句没说完的话。
    - **验证方法（注意）**：代码里用的是 `log.debug`，Spring Boot 默认只打印 INFO 及以上，**不配日志级别是看不到的**。要么临时改 `log.info`，要么在 `application.yml` 里加 `logging.level.com.example.helpdesk: debug`。

### 待办 F：W7-① 文档异步处理（设计已定，2026-09-30）

**要解决什么**：`KnowledgeBaseService.upload()` 现在是**同步**的——一份 20 块的文档要"逐块调百炼向量化 + 逐块写 ES"，几十次 HTTP 往返全压在接口里，响应几十秒（前端 axios 超时 30 秒会直接断）；中途失败还留孤儿 `kb_chunk`（踩坑 17）。**这正是待办 A 第 7 项搁置的那个问题。**

**目标**：上传接口只做"落库 + 发消息"，**毫秒级返回**；处理搬到 consumer，**失败自动重试**，超限进死信；文档状态可查。

**Topic / Tag**
- Topic `kb-doc-process`，Tag `chunk`（MVP 一个消费者够用，不为分类过度设计）

**消息体 —— ★ 只传 ID，不传正文**
```json
{ "docId": 123, "attempt": 0 }
```
- 为什么不传正文：① MQ 消息体越小越好（RocketMQ 默认上限 4MB）② **MySQL 是正本的权威**，正文以库为准，避免"消息里的数据和库里不一致" ③ consumer 自己查库，天然拿到最新状态
- ⚠️ **但前提是"发消息那一刻数据已经提交"** → 发送时机必须在**事务提交之后**（与踩坑 28 同源）。两种做法：`@TransactionalEventListener(phase = AFTER_COMMIT)`，或 RocketMQ 的事务消息 `sendMessageInTransaction`

**消费幂等（三道防线）**
1. **状态判断**：consumer 一进来先查 `kb_document.status`，已经是 `READY` 就直接 ACK 跳过（用**业务状态**当幂等键，和 `resolved` 同一个思路）
2. **确定性 ID 让 ES 写入天然幂等**：`es_id = doc-<docId>-<chunkIndex>` 是确定的 → 重复写就是**覆盖**，不会产生重复文档
3. **重试前先清理**：见下

**重试与死信 —— ★ 不用 MQ 默认的 16 次**
- RocketMQ 默认消费失败重试 16 次、间隔递增。但我们**知道每次重试的成本**（打百炼 API = 烧钱 + 可能触发限流）→ **自己控制次数**
- 设计：消费失败 → 消息体 `attempt + 1` 重新投递，延迟 10s / 30s / 60s；`attempt >= 3` → 置文档 `FAILED` + 投到死信 topic `kb-doc-process-DLQ`（留人工介入）
- **这属于"业务感知的重试策略"**：基础设施给的是"能重试"，重试几次、间隔多久由业务决定

**部分成功怎么办（20 块第 15 块挂了）**
- 前 14 块已经在 MySQL + ES 里了。重试时**先按 docId 清掉已写入的 chunk（MySQL delete + ES delete_by_query），再从第 0 块重做**
- 为什么不搞断点续传：简单、结果确定。"**幂等 = 重复执行结果一样**"，先清理再重做就是最朴素的幂等
- 代价：白算前 14 块的向量。换来的是"任何一次重试完，状态都一样"，值得

**文档状态流转**
```
上传：insert kb_document (PENDING) → 发消息 → 返回 docId（毫秒级）
消费开始：PENDING → PROCESSING
成功：PROCESSING → READY（回填 chunk_num）
失败 3 次：PROCESSING → FAILED
```
- 现在 `KbDocument` 没有"失败原因"字段 → 先只打日志；真要排查时再 V2 迁移加 `error_msg`（V2 只增不改，随时可加）

**开工前环境准备**
1. 服务器装 RocketMQ（Docker）。**踩坑 15 的坑照旧**：`get.docker.com` 连不上 → 用阿里云 docker-ce 源 + 已有的腾讯内网镜像加速器
2. ⚠️ **FinalShell 多行粘贴不可靠 → 一律单行命令**
3. ⚠️ **端口安全**：NameServer `9876` + Broker `10911` **绝不能裸开公网**（与 ES 9200 完全同一条教训）
4. ⚠️ **`brokerIP1` 是个经典坑**：Broker 注册到 NameServer 的地址必须是**客户端能连通的地址**。容器里的内网 IP 客户端连不上 → 必须显式配成客户端可达的 IP

## 踩坑记录（面试素材，随做随记）

1. **主类包名拼错 `hepldesk` → 接口 404**：`@SpringBootApplication` 的 `@ComponentScan` 只扫描主类所在包及子包；所有业务类必须放在主类包正下方。
2. **Spring Initializr 向导无 3.x 选项**：向导联网 start.spring.io（被墙）且默认只给最新 4.x；改用手动 Maven + pom 写死 parent `3.5.3` 走阿里云镜像。生态组件对 4.x 适配未跟上，项目锁 3.5.x。
3. **LF/CRLF 换行警告**：Windows 与 Git 换行符差异，无害；可用 `.gitattributes`（`* text=auto`）统一，暂未加。
4. **登录报"密码错误"真相**：`CommandLineRunner` 只在启动时执行一次，改完 `DataInitializer` 没彻底重启（热重载不算）→ 占位密码没被替换。教训：启动初始化类代码必须完全停进程再启。
5. **用 GET 访问 POST 接口**：浏览器地址栏发 GET，登录接口是 POST → `HttpRequestMethodNotSupportedException`。
6. **拦截器路径写 `/api/console/` 缺 `**`**：只匹配路径本身 → 子路径全裸奔；叠加 `Map.of` 不允许 null（UserContext 空时 NPE）→ 500。
7. **404/405 被兜底成 500**：`Exception.class` 大网把请求错误也包装成"系统繁忙"（已补 `NoResourceFoundException` 处理器解决 404 部分）。
8. **前端报"网络错误"= 后端 8080 没启动**：排查顺序：先 `localhost:8080/api/health`，再看 F12 Console。
9. **跨域解法**：前端 vite proxy 把 `/api` 转发到 8080，浏览器只见同源，OPTIONS 预检消失（后端放行 OPTIONS 的逻辑保留）。
10. **GLM 接入连环坑（已转 DeepSeek）**：① 未实名 → key 全 401；② Git Bash 发中文 → GBK → 400 UTF-8 错误；③ Spring AI 默认拼 `/v1/chat/completions`，GLM 只认 `/v4/` → 404，需 `completions-path: /chat/completions`（该属性靠解 jar + javap 挖出）；④ `glm-4.7-flash` 免费模型持续 1305 繁忙。
11. **MySQL 8 报 `Public Key Retrieval is not allowed`**：JDBC URL 加 `allowPublicKeyRetrieval=true`。
12. **"找不到 ChatClient Bean"**：Spring AI 自动配置只给 `ChatClient.Builder`，需自建 `@Bean ChatClient`（`AiConfig`）。
13. **SSE 前端三坑**：① 网络把多个 token 打包到达 → 前端"打字机节奏器"（队列 + 每 15ms 吐一字）平滑播放；② **Vue3 响应式坑**：对象 push 进 ref 数组后，局部变量仍指向原始对象，改它不触发渲染 → 必须改 `messages.value[下标]`；③ Enter 发送/Shift+Enter 换行用 `@keydown.enter.exact.prevent`。
14. **流式接口协议**：SSE 事件 `visitor`(回执 JSON) → **`references`(引用来源 JSON 数组)** → `token`(逐字，可多次) → `done`(落库后的完整消息 JSON) / `error`；前端用 `fetch`（非 axios）+ `ReadableStream`，帧按空行 `\n\n` 切分。
    - **顺序说明（2026-09-21 起以实际实现为准）**：`references` 在 `token` **之前**——检索在模型开始回答前就完成了，早发前端早准备。
    - `references` 是 **W5 新增**的事件，在 `done` 之前发，payload `[{documentId, docTitle, chunkIndex, score, snippet}]`。
    - `done` 保持"落库后的完整消息"这一语义，**不与 references 混用**（不要为了省一个事件把引用塞进 done 的 payload）。
    - 旧协议（无 `references`）已在 2026-09-16 归档，见 decision-log 同日条目。
    - **完整事件清单（2026-09-30 实测核对 `event().name(...)` 全库扫描）**——注意有**两条独立的 SSE 通道**：
      - **A. 访客发消息的流式响应**（`POST /api/v1/conversations/{id}/messages`，`fetch` 读流）：`visitor` → 之后二选一：① **人工分支**只回 `waiting` 就关连接（`humanMode` 命中时跳过检索与模型）② **AI 分支** `references` → `token`(多次) → `done`；出错走 `error`
        - ⚠️ **`waiting` 的语义是"状态"，不是"一条提示消息"**：人工模式下**每发一条消息**都会回它（那个人工分支里根本没调模型，"没人答"这个事实每条消息都成立）。前端只能把它当**状态信号**（点亮常驻标识），**绝不能插成聊天气泡** —— 否则访客每发一条就多一条"已转接人工客服"。详见踩坑 26
      - **B. 长连接实时通道**（`GET /api/v1/conversations/{id}/stream`，`EventSource` 订阅）：连上先回 `connected` 握手，之后由 `SseSessionRegistry.push` 主动推 —— 目前只用了 `agent`（坐席消息）；`system`（系统提示）**已预留但还没接**（见挂起项）

22. **端口占用导致"前端已在运行"的误判（2026-09-21）**：本机另一个项目 `D:\项目\drone-connect\drone-ground-station` 的 dev server 默认占 **5173**，访问 `localhost:5173` 能返回 HTTP 200，于是误判成"AI 客服前端已经在跑"，用户打开看到的却是无人机项目的页面。**教训：判断前端是否可用要看页面内容（`<title>` 是否为"AI 客服"），不能只看状态码。** 已把本项目前端固定为 `5174` + `strictPort: true`。
23. **`SseEmitter` 不会自己从 Map 里消失 → 内存泄漏（2026-09-30）**：把 `SseEmitter` 存进 `Map` 做长连接登记后，访客一关页面连接就死了，但**对象还被 Map 引用着，GC 收不掉**：内存一路涨，`push` 时还会挨个给死连接白试一遍。解法：`register` 时就把清理动作**绑成回调**（`onCompletion` / `onTimeout` / `onError` → `remove`），并让 `remove` **幂等**（重复调用不报错）+ 清掉空列表的 key。**注意区分**：`remove` 是普通方法，`() -> remove(...)` 才是回调——不能直接写 `onCompletion(remove(...))`，那会立刻执行且类型不匹配。
24. **`@RequestParam` 参数名拼错 = 静默失效（2026-09-30）**：坐席消息接口把 `lastId` 写成 `lasteId`，由于 `required = false`，前端传 `?lastId=` 时**不报错**，只是参数永远为 `null` → 每次返回最新一页，**翻页功能悄悄失灵**。教训：可选参数拼错比必填参数拼错更危险（不报错的 bug 最难查）；同类坑还有漏写 `@RequestParam(name = ...)`。
25. **后端加了 SSE 事件、前端忘了接 → 静默无提示（2026-09-30）**：转人工后端做了降级分支（`humanMode` 命中时只回 `waiting` 然后关连接），但 `Chat.vue` 的事件处理里只有 `visitor/references/token/done/error`，**没有 `waiting` 分支** → 访客发消息后页面**什么都不发生**（`sending` 被 `finally` 复位，看起来像"没反应"），既不报错也没提示，极难排查。**教训：SSE 是"协议"，新加事件必须两端同步清单——后端加了 `X`，前端必须有 `case X`。** 排查手法：全库 `grep "event().name("` 列出后端真正发过的所有事件名，再和前端的分支逐个对照。
26. **一个 SSE 事件混了两种语义 → 每发一条消息刷一条提示（2026-09-30）**：`waiting` 事件的 data 是一句**给人看的话**（"已转接人工客服，坐席会尽快回复"），但它的触发时机是"人工模式下**每收到一条消息**"。前端把它当**消息**插成气泡 → 访客每发一条就多一条"已转接人工客服"，看起来像被反复转接。**根因：一个事件同时承担了"状态"和"提示"两种语义。** 解法：事件只表达状态（前端点亮标题栏的常驻标识"人工客服接入中"），**一次性提示交给落库的 SYSTEM 消息**——`escalateToAgent` 本来就写了"已为您转接人工客服，请稍后"，它只出现一次、刷新页面也还在。**通用原则：SSE 事件要么是"消息"要么是"状态"，不要混**（同类问题见第 14 条 `done` 与 `references` 不混用）。
27. **三个各自合理的设计，组合起来把访客"锁死"了（2026-09-30）**：① **匿名访客**——`POST /api/v1/conversations` 每调一次就新建一个访客 + 一个新会话；② **会话状态单向**——`AI → AGENT` 之后，后端**没有任何代码把它改回 `AI`**；③ **前端把 `conversationId` 存进 localStorage 永久复用**。单独看每条都合理，合起来的后果是：**访客一旦被转人工，在这个浏览器里之后发的每条消息都会走"人工分支"，永远拿不到 AI 回复，而且无路可退**（只能手动清 localStorage）。**修法：加「新对话」按钮（已加）** —— 它不只是体验优化，而是转人工后唯一的出口。更彻底的方案是给会话加生命周期（坐席关闭会话 / 超时自动关闭 → 访客下一条消息自动开新会话），留到 W7-9。**教训：要盯"多个合理设计的组合后果"，单看每个模块都挑不出毛病。**
28. **事务里做了"不可回滚"的副作用（2026-09-30）**：`saveSystemMessage` 里加了 `registry.push(...)` 之后，它是一个会被 `markResolved`（`@Transactional`）调用的方法 —— 于是**推送发生在事务提交之前**。链条是：`update resolved`（可回滚）→ `工单流转`（可回滚）→ `insert message` + `update lastMessageAt`（可回滚）→ **`registry.push`（★ 不可回滚，消息已经写到访客浏览器上了）** → commit。两种翻车方式：① **commit 失败**（死锁/连接断）→ 数据全回滚，但访客屏幕上已经有"感谢您的反馈"了；② **更常见**：事务还没提交的那几毫秒里访客通过 SSE 收到了推送，此时他刷新页面拉历史，**库里还查不到这条消息** → 消息"闪现又消失"。**原则：事务里不要做不可回滚的副作用（推送、发短信、调外部 API 全是）。** 正确做法是让副作用等提交之后执行：`TransactionSynchronizationManager.registerSynchronization(...)` 的 `afterCommit()`，或发事件 + `@TransactionalEventListener(phase = AFTER_COMMIT)`。**"一件事做完了"和"别人知道你做完了"是两个时刻，中间不能乱。** 归属 W7（"事件通知"场景一次性做对）。
